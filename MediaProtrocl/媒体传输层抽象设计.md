# 媒体传输层抽象设计

> 从一个 RTSP 播放器出发，提炼媒体传输层的共性框架，覆盖 RTSP / RTMP / ONVIF / GB28181 / WebRTC 五种协议。

---

## 一、为什么需要抽象？

### 1.1 问题起点

你写了一个 MiniFFmpegPlayer，只支持 RTSP。产品经理说：

- "加个 GB28181 吧，公安系统要接"
- "RTMP 直播也要支持"
- "客户要求 WebRTC 低延迟"

如果每种协议都从头写一遍播放器——连接、协商、解码、显示——代码重复 80%，维护噩梦。

### 1.2 解决思路

**找出不变的共性，封装变化的个性。**

这正是 SOUL.md 里写的：

> 接口比实现更稳定。先想清楚接口契约，再实现。

---

## 二、媒体传输层在做什么？

### 2.1 五步模型

不管什么协议，媒体传输层做的事情可以归纳为五步：

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ ① 建立连接│──▶│ ② 协商参数│──▶│ ③ 传输数据│──▶│ ④ 质量控制│──▶│ ⑤ 结束传输│
│          │   │          │   │          │   │          │   │          │
│ 握手/认证 │   │ 编解码器  │   │ 视频帧    │   │ 丢包重传  │   │ 优雅关闭  │
│ 建立通道  │   │ 分辨率    │   │ 音频帧    │   │ 抖动缓冲  │   │ 释放资源  │
│          │   │ 帧率/码率 │   │          │   │ 带宽自适应│   │          │
└──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

### 2.2 每一步的含义

| 步骤 | 做什么 | 输入 | 输出 |
|------|--------|------|------|
| ① 建立连接 | 网络握手、身份认证、建立传输通道 | URL + 凭据 | 连接句柄 |
| ② 协商参数 | 交换媒体能力（编解码器、分辨率、帧率） | 本端能力 | 双方共识的 MediaInfo |
| ③ 传输数据 | 按协商好的格式搬运音视频帧 | 网络数据包 | AVPacket（压缩帧） |
| ④ 质量控制 | 监控传输质量，自适应调整 | 丢包率、抖动、RTT | 调整决策（码率/重传） |
| ⑤ 结束传输 | 通知对端、释放资源 | 停止指令 | 干净的关闭 |

## 三、五种协议的个性对比

### 3.1 对照表

| 共性步骤 | RTSP | RTMP | ONVIF | GB28181 | WebRTC |
|---------|------|------|-------|---------|--------|
| **① 建立连接** | TCP 信令通道（默认554端口） | TCP 握手（1935端口） | HTTP SOAP（3702发现/80端口） | SIP REGISTER（5060端口） | ICE 候选交换 + DTLS 握手 |
| **② 协商参数** | DESCRIBE → SDP | handshake → AMF 元数据 | GetProfiles → SOAP XML | SIP INVITE → SDP | SDP Offer/Answer |
| **③ 传输数据** | RTP over UDP/TCP（interleaved） | FLV chunk over TCP | RTP（底层走 RTSP） | RTP over UDP（PS 封装） | SRTP over UDP |
| **④ 质量控制** | RTCP SR/RR | 无（TCP 保证可靠性） | RTCP | RTCP | RTCP + NACK + FEC + 带宽估计 |
| **⑤ 结束传输** | TEARDOWN | close TCP | HTTP close | SIP BYE | DTLS close |
| **默认端口** | 554 | 1935 | 3702/80 | 5060 | 临时端口 |
| **传输层** | TCP（信令）+ UDP/TCP（媒体） | TCP（全部） | HTTP + RTP | UDP（媒体）+ TCP（信令） | UDP（全部） |
| **延迟** | 中（1-3秒） | 高（3-10秒） | 中（1-3秒） | 中（1-3秒） | 低（<1秒） |
| **典型场景** | 监控摄像头 | 直播推流 | 安防设备发现 | 公安监控联网 | 视频通话/会议 |

### 3.2 数据封装格式对比

```
RTSP:     RTP 包 → 裸 H.264/H.265 NALU（每个 RTP 包放一个 NALU 或分片）
RTMP:     FLV chunk → H.264 NALU（带 4 字节长度前缀，不带起始码 00 00 00 01）
ONVIF:    同 RTSP（ONVIF 底层就是 RTSP）
GB28181:  RTP 包 → PS 流 → PS 包内封装 H.264/H.265 NALU（多了一层 PS 封装）
WebRTC:   SRTP 包 → RTP 包 → 裸 H.264/VP8/AV1 NALU（加密传输）
```

**GB28181 比 RTSP 多了一层 PS 封装**——这是它最显著的特征。你在 6/1 的实战中已经解析过 PS 流，知道 PS 包的结构（PS Header → System Header → PSM → PES Packet）。

### 3.3 信令通道对比

```
RTSP:     自己设计的文本协议（类似 HTTP，每条请求有 CSeq 序列号）
RTMP:     自己设计的二进制协议（AMF0/AMF3 编码）
ONVIF:    HTTP + SOAP XML（Web Service 标准）
GB28181:  SIP 协议（文本协议，类似 HTTP，但有REGISTER/INVITE/BYE 等方法）
WebRTC:   没有固定信令通道——通过外部渠道（WebSocket/HTTP）交换 SDP
```

**WebRTC 最特殊**——它的信令不在协议内部定义，需要应用层自己实现（通常用 WebSocket）。

## 四、抽象层设计

### 4.1 接口定义（IMediaTransport）

```cpp
// ================================================================
// 媒体信息（协商结果的载体）
// ================================================================
struct MediaInfo
{
    // 视频
    QString videoCodec;     // "H.264" / "H.265" / "VP8" / "AV1"
    int     videoWidth;     // 1920
    int     videoHeight;    // 1080
    int     videoFps;       // 25
    int     videoBitrate;   // 4000000 (bps)

    // 音频
    QString audioCodec;     // "AAC" / "G.711" / "Opus"
    int     audioSampleRate;// 44100
    int     audioChannels;  // 1（单声道） / 2（立体声）

    // 传输
    QString transport;      // "TCP" / "UDP" / "SRTP"
    bool    isEncrypted;    // WebRTC 用 SRTP 加密
};

// ================================================================
// 抽象接口：媒体传输层
// ================================================================
class IMediaTransport
{
public:
    virtual ~IMediaTransport() {}

    // ① 建立连接
    //    RTSP:  avformat_open_input（内部完成 OPTIONS/DESCRIBE/SETUP/PLAY）
    //    GB28181: SIP REGISTER + SIP INVITE
    //    WebRTC: ICE + DTLS
    virtual bool connect(const QString &url) = 0;

    // ② 协商参数
    //    RTSP/GB28181: 解析 SDP
    //    RTMP: 解析 AMF 元数据
    //    WebRTC: 解析 SDP Offer/Answer
    virtual bool negotiate(MediaInfo &info) = 0;

    // ③ 取一帧数据
    //    所有协议最终都输出 AVPacket（FFmpeg 的统一格式）
    //    阻塞或非阻塞取决于实现
    virtual bool readFrame(AVPacket *pkt) = 0;

    // ④ 质量反馈（可选实现）
    //    RTSP/GB28181: RTCP SR/RR
    //    WebRTC: RTCP + NACK + REMB
    //    RTMP: 空实现（TCP 保证可靠性）
    virtual void onQualityReport(int lostPackets, int jitter, int rttMs) {
        (void)lostPackets; (void)jitter; (void)rttMs;  // 默认空实现
    }

    // ⑤ 断开
    //    RTSP: TEARDOWN
    //    GB28181: SIP BYE
    //    WebRTC: DTLS close
    virtual void disconnect() = 0;

    // 中断回调（FFmpeg 阻塞操作的逃生门）
    // 所有基于 FFmpeg 的实现都需要这个
    static int interruptCallback(void *opaque);
};
```

### 4.2 类图关系

```
                    ┌─────────────────┐
                    │  IMediaTransport │  ← 抽象接口
                    │  (纯虚函数)       │
                    └────────┬────────┘
                             │
          ┌──────────┬───────┼────────┬──────────┐
          │          │       │        │          │
          ▼          ▼       ▼        ▼          ▼
    ┌──────────┐┌─────────┐┌──────┐┌────────┐┌─────────┐
    │RtspTrans-││RtmpTrans││Onvif ││GB28181 ││WebRTC   │
    │port      ││port     ││Trans ││Transport││Transport│
    │          ││         ││port  ││        ││         │
    │FFmpeg    ││FFmpeg   ││FFmpeg││FFmpeg  ││自实现    │
    │原生支持   ││原生支持  ││原生  ││原生支持 ││ICE/DTLS │
    └──────────┘└─────────┘└──────┘└────────┘└─────────┘
```

### 4.3 MiniPlayer 怎么用这个抽象

```cpp
class MiniPlayer : public QThread
{
private:
    IMediaTransport *transport_;   // 指向抽象，不指向具体

    void run() {
        MediaInfo info;

        if (!transport_->connect(url_))        // 不管什么协议，都是 connect
            return;
        if (!transport_->negotiate(info))      // 不管什么协议，都是 negotiate
            return;

        while (b_playing_) {
            AVPacket pkt;
            if (!transport_->readFrame(&pkt))  // 不管什么协议，都是 readFrame
                break;
            // 解码 → 转换 → emit
        }

        transport_->disconnect();
    }
};

// 使用时注入具体实现：
MiniPlayer player;
player.setTransport(new RtspTransport());        // 今天播 RTSP
// player.setTransport(new GB28181Transport());  // 明天接 GB28181
// player.setTransport(new WebRTCTransport());   // 后天试 WebRTC
```

**上层完全不变，换底层实现就行。**

## 五、各协议实现要点

### 5.1 RtspTransport

```cpp
class RtspTransport : public IMediaTransport
{
private:
    AVFormatContext *fmt_ctx_;

public:
    bool connect(const QString &url) override {
        fmt_ctx_ = avformat_alloc_context();
        fmt_ctx_->interrupt_callback.callback = interruptCallback;
        fmt_ctx_->interrupt_callback.opaque = this;

        AVDictionary *opts = nullptr;
        av_dict_set(&opts, "rtsp_transport", "tcp", 0);    // TCP 模式
        av_dict_set(&opts, "stimeout", "5000000", 0);      // 5 秒超时

        int ret = avformat_open_input(&fmt_ctx_, url.toUtf8().constData(),
                                       nullptr, &opts);
        av_dict_free(&opts);
        return ret >= 0;
    }

    bool negotiate(MediaInfo &info) override {
        avformat_find_stream_info(fmt_ctx_, nullptr);
        // 从 fmt_ctx_->streams[i]->codecpar 提取 MediaInfo
        // ...
        return true;
    }

    bool readFrame(AVPacket *pkt) override {
        return av_read_frame(fmt_ctx_, pkt) >= 0;
    }

    void disconnect() override {
        avformat_close_input(&fmt_ctx_);
    }
};
```

**特点：** FFmpeg 原生支持，`avformat_open_input` 内部完成 OPTIONS/DESCRIBE/SETUP/PLAY 四步。

### 5.2 GB28181Transport

```cpp
class GB28181Transport : public IMediaTransport
{
private:
    AVFormatContext *fmt_ctx_;

public:
    bool connect(const QString &url) override {
        // GB28181 的 URL 格式：gb28181://sip:xxx@xxx
        // FFmpeg 内部处理 SIP 注册和 INVITE
        fmt_ctx_ = avformat_alloc_context();
        AVDictionary *opts = nullptr;
        av_dict_set(&opts, "rtsp_transport", "udp", 0);  // GB28181 通常用 UDP
        int ret = avformat_open_input(&fmt_ctx_, url.toUtf8().constData(),
                                       nullptr, &opts);
        av_dict_free(&opts);
        return ret >= 0;
    }

    bool readFrame(AVPacket *pkt) override {
        // FFmpeg 自动处理 RTP → PS 拆包 → 裸 H.264
        // 对上层来说和 RTSP 没区别
        return av_read_frame(fmt_ctx_, pkt) >= 0;
    }
    // ...
};
```

**特点：** 多了一层 PS 封装，但 FFmpeg 内部自动拆解，上层接口一样。你在 6/1 实战中解析过的 PS 流结构（PS Header → System Header → PSM → PES），FFmpeg 帮你做了。

### 5.4 OnvifTransport

```cpp
class OnvifTransport : public IMediaTransport
{
public:
    bool connect(const QString &url) override {
        // ONVIF 分两步：
        // 1. WS-Discovery（UDP 多播 239.255.255.250:3702）发现设备
        // 2. GetProfiles → GetStreamUri 获取 RTSP 地址
        // 3. 拿到 RTSP 地址后，走 RtspTransport
        QString rtspUrl = discoverAndResolve(url);
        return innerRtsp_.connect(rtspUrl);
    }
    // ...
private:
    RtspTransport innerRtsp_;  // 组合：ONVIF 内部用 RTSP
};
```

**特点：** ONVIF 本质是"设备发现 + RTSP"——发现阶段用 SOAP XML，拿到 RTSP 地址后走标准 RTSP。这就是组合模式（Composition over Inheritance）。

## 六、SOLID 原则对照

| 原则 | 体现 |
|------|------|
| **S** 单一职责 | IMediaTransport 只定义"传输"接口，不管解码、不管显示 |
| **O** 开闭原则 | 加新协议（如 SRT）→ 新增 SrtTransport 类，不改现有代码 |
| **L** 里氏替换 | MiniPlayer 持有 `IMediaTransport*`，换任意子类行为不变 |
| **I** 接口隔离 | 接口只有 5 个方法，不把解码/渲染混进来 |
| **D** 依赖倒置 | MiniPlayer 依赖抽象接口，不依赖具体的 RtspTransport |

### 对应 OOP 思想

```
封装：每种协议的实现细节藏在子类里，上层看不到
继承：RtspTransport 继承 IMediaTransport，复用接口定义
多态：transport_->connect() 调的是哪个实现，运行时决定
抽象：IMediaTransport 定义了"做什么"，子类决定"怎么做"
```

## 七、FFmpeg 内部已经做了这层抽象

你其实已经在用了——`avformat_open_input()` 就是 `IMediaTransport::connect()`：

```cpp
// 同一个函数，传不同 URL 协议头，FFmpeg 内部自动选不同的协议处理器
avformat_open_input(&ctx, "rtsp://...", ...);     // → 内部 RtspTransport
avformat_open_input(&ctx, "rtmp://...", ...);     // → 内部 RtmpTransport
avformat_open_input(&ctx, "gb28181://...", ...);  // → 内部 GB28181Transport
avformat_open_input(&ctx, "file://...", ...);     // → 内部 FileTransport
```

FFmpeg 内部的 `URLProtocol` 结构体就是 `IMediaTransport` 的 C 语言版本：

```c
// FFmpeg 源码：libavformat/url.h
typedef struct URLProtocol {
    const char *name;
    int  (*url_open)(URLContext *h, const char *url, int flags);
    int  (*url_read)(URLContext *h, unsigned char *buf, int size);
    int  (*url_close)(URLContext *h);
    // ...
} URLProtocol;
```

**你设计的 C++ 接口，和 FFmpeg 的 C 语言 vtable，本质是同一个东西——只是语言不同。**

### FFmpeg 覆盖范围

| 协议 | FFmpeg 原生支持 | 说明 |
|------|----------------|------|
| RTSP | ✅ | avformat_open_input 内部完成全部 RTSP 交互 |
| RTMP | ✅ | 同上 |
| GB28181 | ✅ | SIP + RTP + PS 一条龙 |
| ONVIF | ✅ | 本质是 RTSP，发现阶段需额外处理 |
| WebRTC | ❌ | ICE/DTLS/SRTP 不完整支持，需自实现 |
| SRT | ✅ | 新型低延迟协议，FFmpeg 4.1+ 支持 |

**WebRTC 是唯一需要跳出 FFmpeg 框架的。**

## 八、设计模式关联

### 8.1 策略模式（Strategy）

```
Context（MiniPlayer）── 持有 ──→ Strategy（IMediaTransport）
                                      ↑
                           RtspTransport / GB28181Transport / ...
```

传输策略可在运行时切换——今天用 RTSP，明天用 GB28181，上层代码一行不改。

### 8.2 工厂模式（Factory）

```cpp
class TransportFactory
{
public:
    static IMediaTransport *create(const QString &scheme) {
        if (scheme == "rtsp")     return new RtspTransport();
        if (scheme == "rtmp")     return new RtmpTransport();
        if (scheme == "gb28181")  return new GB28181Transport();
        if (scheme == "webrtc")   return new WebRTCTransport();
        return nullptr;
    }
};

// 使用：
QString url = "rtsp://192.168.1.100/stream";
QString scheme = url.section("://", 0, 0);  // "rtsp"
IMediaTransport *t = TransportFactory::create(scheme);
```

URL 的协议头自动决定用哪个实现——调用方不需要知道有哪些子类。

### 8.3 适配器模式（Adapter）

```
FFmpeg 的 avformat_open_input 已经是一种"传输实现"
但它不实现 IMediaTransport 接口

RtspTransport 就是适配器：
  把 FFmpeg 的 C API 适配为 IMediaTransport 的 C++ 接口

┌──────────────┐     ┌──────────────┐     ┌─────────────┐
│ MiniPlayer   │────▶│ RtspTransport│────▶│ FFmpeg C API│
│ (C++ 上层)   │     │ (Adapter)    │     │ (C 底层)    │
└──────────────┘     └──────────────┘     └─────────────┘
```

### 8.4 组合模式（Composition）

ONVIF 的实现：

```
OnvifTransport 内部组合了 RtspTransport：

┌──────────────────┐
│ OnvifTransport   │
│  ├── SOAP 发现    │  ← 自己实现
│  ├── GetProfiles  │  ← 自己实现
│  └── RtspTransport│  ← 组合已有实现
│       └── connect │
│       └── readFrame│
└──────────────────┘
```

**优先组合 over 继承**——ONVIF 不是"一种 RTSP"，而是"包含 RTSP"。

## 十、从 MiniPlayer 到抽象框架的演进路线

```
阶段 1（你现在）：MiniFFmpegPlayer
  └── 只支持 RTSP，5 步流水线写死在一个类里

阶段 2：提取接口
  └── 把 5 步流水线抽象为 IMediaTransport
  └── MiniPlayer 通过指针调用抽象接口

阶段 3：多协议实现
  └── RtspTransport（现有代码重构）
  └── GB28181Transport（复用你的 PS 流经验）
  └── RtmpTransport（FFmpeg 原生支持）

阶段 4：工厂 + 配置化
  └── TransportFactory 根据 URL 自动选择
  └── 配置文件指定默认协议参数

阶段 5：WebRTC 支持
  └── 引入 libwebrtc
  └── WebRTCTransport 实现 IMediaTransport
  └── 需要自建 RTP 栈，跳出 FFmpeg 框架
```

**每个阶段都是上一个阶段的重构——不是推倒重来。**

---

## 十一、总结

### 共性与个性的关系

```
共性（IMediaTransport 接口）     个性（各子类实现）
──────────────────────────────────────────
connect()                  →   RTSP: OPTIONS/DESCRIBE/SETUP/PLAY
                           →   GB28181: SIP REGISTER/INVITE
                           →   WebRTC: ICE/DTLS

negotiate()                →   都可能用 SDP，但字段含义不同
                           →   RTMP 用 AMF 元数据
                           →   ONVIF 用 SOAP XML

readFrame()                →   RTSP: RTP 裸 H.264
                           →   GB28181: RTP 包 PS 流
                           →   RTMP: FLV chunk

disconnect()               →   RTSP: TEARDOWN
                           →   GB28181: SIP BYE
                           →   WebRTC: DTLS close
```

**抽象层定义"做什么"，实现层决定"怎么做"。这就是 OOP 的精髓。**

### 一句话

> 五种协议，五步流水线。共性提炼为接口，个性封装为实现。
> FFmpeg 已经帮你做了大部分——但 WebRTC 是那个跳出框架的例外。
